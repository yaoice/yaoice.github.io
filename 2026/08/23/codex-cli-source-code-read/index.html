Codex OpenAI Rust 源码解读 AI Agent

OpenAI Codex CLI 源码解读：一个 Rust 写成的 AI 编码代理内核

从一个 Rust workspace 拆解事件驱动的 Agent 循环、四层安全防御与多 Agent 协作体系

Posted by iceyao on Sunday, August 23, 2026

引言：读 Codex 源码的理由

过去两年，AI 编码代理经历了从玩具到生产力的跃迁。在这条赛道上，Codex CLI 是最值得工程师研究的样本之一：它是 OpenAI 官方的本地编码代理，用 Rust 从零重写，仓库规模超过一百万行，却保持着清晰的模块边界；它同时服务终端、IDE 插件和桌面应用三种形态；它的命令执行安全模型、会话恢复机制、多 Agent 协作协议，都是生产环境里"跑过量"的设计。

读它的源码，最大的收获不是某个具体算法的实现，而是一整套工程决策：异步事件流如何组织、模型生成的代码为何不能被信任、状态如何持久化才能让对话"随时复活"。本文基于仓库当前源码逐层拆解，读完后你应该能回答四个问题：Agent 的 turn 循环到底长什么样？一条 shell 命令要穿过几道关卡才能真正执行？一个 Agent 怎么派生出一群子 Agent 而不失控？换个终端、重启电脑之后，对话为什么还能原样恢复？

技术栈与仓库总览

仓库是典型的 Rust workspace monorepo：codex-rs/ 下挂着上百个 crate，核心二进制是 codex，但真正的主入口在 codex-rs/cli/——一个名为 MultitoolCli 的"多合一"二进制，通过 arg0 分发到不同子命令（exec、login、app-server、doctor 等），没有子命令时落到交互式 TUI。

值得注意的几点：

  • 构建系统双轨：Cargo 与 Bazel 并存（MODULE.bazel、defs.bzl），AGENTS.md 要求改动 Cargo 依赖时必须同步刷新 Bazel 锁文件，保证 CI 的远程构建缓存可用；
  • Rust 为主、多语言协作：协议层用 Rust 定义、经宏生成 TypeScript（app-server-protocol 下有 679 个 .ts 文件），给 IDE 插件用；codex-cli/ 是一个薄薄的 npm 包装，只负责按平台挑选预编译二进制并转发信号；sdk/ 提供 Python/TS SDK；
  • 工程纪律高度内化：AGENTS.md 里有"抵制向 codex-core 加代码"“模块不超过 500 行"“注入模型上下文必须有硬上限（单条不超过 10K token）“这类约束，是一个成熟团队管理大型 Rust 项目的缩影。

架构总览：多入口，单内核

Codex 的架构可以概括为多入口、单内核。无论用户从终端、IDE 还是桌面应用进来，最终都汇聚到 codex-core 的同一个事件循环：

入口层有三个值得注意的设计：

  • TUI（codex-rs/tui/）：默认交互入口，基于 ratatui。它不是一个严格 Elm 式的 App/View/update 结构，而是 App 持有全部状态 + 一个 select! 事件循环同时监听键盘事件、来自 core 的 ThreadBufferedEvent 与 app-server 事件；
  • codex exec（codex-rs/exec/）：非交互入口，面向 CI 与脚本，支持 --json 输出 JSONL、--output-schema 结构化输出，是"把 Agent 当函数用"的形态；
  • app-server（codex-rs/app-server/）：一个本地 JSON-RPC 服务，支持 stdio、WebSocket、Unix Socket 三种传输，thread/start、turn/start 等 API 直接服务 VS Code 扩展这类富客户端——这就是 Codex 的"IDE 插件"背后的真实形态。安全上值得一提：stdio 靠管道、Unix Socket 靠文件权限，唯独 WebSocket 需要显式认证（能力令牌或 HS256 JWT），监听非 loopback 地址却未配置认证时直接拒绝启动——把"默认不安全就拒绝"写进了启动逻辑。

核心功能解析

Turn 事件循环：Op 进、EventMsg 出

理解 Codex 的钥匙是它的事件协议（codex-rs/protocol/）。协议采用"提交队列 / 事件队列"模式：客户端提交 Op（TurnInput、Interrupt、ExecApproval、Compact 等），服务端流回 EventMsg（TurnStarted、AgentMessageContentDelta、ExecCommandBegin、ApprovalRequest 等约 90 种事件变体）。TUI 和 app-server 本质上是同一个协议的两种渲染器。

一次 turn 的完整闭环是这样的：

Session（core/src/session/session.rs）持有一个事件发送通道和一个 InputQueue，每个 Session 同一时刻最多运行一个 turn。run_turn 循环做三件事：组装 Prompt（历史 + 工具清单 + 系统指令）→ 向模型采样 → 根据响应分流。如果模型返回 function call，就执行工具并把输出作为 FunctionCallOutput 追加进下一轮采样请求；返回文本则增量渲染给用户，直到 Completed 事件结束 turn。

有两个实现细节特别漂亮：

一是 turn 的"挂起"不是状态枚举，而是 oneshot 通道。 TurnState（core/src/state/turn.rs）里维护着几组 HashMap<String, oneshot::Sender<_>>：pending_approvals、pending_user_input、pending_elicitations。当模型请求执行一条需要审批的命令时，turn 就挂在一个 oneshot::Sender 上等待用户决定。这意味着"等待审批"“等待输入"不是 if-else 分支，而是天然支持任意并发挂起点的异步原语——用户按一下回车，对应的 oneshot 被唤醒，循环原地继续。

二是依赖注入按粒度分层。 TurnContext 承载 turn 级依赖（配置、模型 provider、环境），StepContext 承载单次采样请求级依赖（MCP 绑定、工具路由、审批策略）。模型中途切换时，重建的只是 StepContext，而不是整个 turn。这是一个很实用的边界划分：什么依赖活多久，决定了它在哪一层注入。

模型抽象与流式协议

模型层的抽象是 ModelProvider trait（codex-rs/model-provider/），其大量方法带有默认实现，任何 OpenAI 兼容后端只需覆写差异部分。实际传输由 ModelClient 完成，支持 HTTP SSE 与 WebSocket 双通道、zstd 压缩、prompt 缓存，以及针对 429/5xx/传输错误的指数退避重试。

请求载荷是 ResponsesApiRequest（codex-api/src/common.rs）：model、instructions、input: Vec<ResponseItem>、tools、reasoning 等字段。响应则是 ResponseEvent 流：OutputTextDelta（文本增量）、ToolCallInputDelta（工具调用参数增量）、ReasoningSummaryDelta（思考摘要增量）、Completed { token_usage, end_turn }（结束标志）。

“思考链"在协议里被拆成三种事件——结构化摘要、原始思维链文本、分段标记——上层按配置（Auto/Concise/Detailed/None）决定展示多少。这个分层让产品可以在"透明度"和"信噪比"之间平滑调节。

命令执行：四层安全防御

Codex 的设计哲学很明确：模型生成的命令不被信任。一条 exec_command 从生成到执行，要穿过四道关卡：

第一层是策略引擎（codex-rs/execpolicy/）。.codexpolicy 规则文件用 Starlark 语法编写：prefix_rule(pattern=[...], decision=...) 按程序首 token 前缀匹配，host_executable 约束绝对路径只能通过 basename 规则解析，network_rule 管控域名级网络访问。多个规则命中时取最严格裁决（forbidden > prompt > allow）。

第二层是危险命令启发式。未命中任何规则的命令落入内置高危前缀表兜底——rm -f、sudo、bash -c、python -c、curl | sh 这类模式会被直接识别，依据审批策略升级为询问或禁止。

第三层是用户审批。approval_policy 有 Never / OnRequest / UnlessTrusted / Granular 四档。审批发生时，TUI 会把命令 diff 摊开给用户看——前面说的 pending_approvals 的 oneshot 通道就在这里生效。

第四层是平台沙箱。SandboxManager::transform() 把命令改写成带沙箱包装器的 argv：Linux 用 bubblewrap 挂只读根文件系统 + user/pid/net 命名空间 + seccomp 网络过滤；macOS 用 sandbox-exec + Seatbelt SBPL 策略文件；Windows 用受限令牌 + WFP 防火墙。三套完全不同的内核原语，被抽象成同一个 SandboxType 枚举。

这四层合在一起，是一份很完整的"不可信输入执行"安全教案——策略做白名单、启发式做兜底、审批做人机闭环、沙箱做最终物理隔离，任何一层失效都有下一层接着。

多 Agent：派生、投递与恢复

Codex 的多 Agent 体系围绕三个机制展开：派生（spawn）、邮箱（mailbox）、身份（identity）。

派生由 AgentRegistry 管理：reserve_spawn_slot 返回一个 SpawnReservation——这是一个 RAII 占位对象，Drop 时自动回滚，只有 commit() 才真正注册。用 Rust 的所有权语义做资源超发保护，优雅得令人拍案。子 Agent 有角色（explorer / worker 等），apply_role_to_config 对子 Agent 施加能力收敛——禁用 shell、apps、插件——权限只降不升。

Agent 之间通过 mailbox 投递消息：send_message 只入队不触发 turn（QueueOnly），followup_task 投递并触发新一轮。thread_spawn_edges 表把父子线程关系落库，恢复会话时 BFS 沿边遍历，把所有 open 的子线程一并复活。

最容易被忽略的是身份问题：每个子 Agent 都通过 agent-identity crate 生成 ed25519 密钥对，以 JWT/JWKS 形式获得后端身份凭证。当几十个子 Agent 并发访问云服务时，“我是谁的哪个子任务"必须是一等公民，而不是拼在 payload 里的字符串。

持久化：SQLite 管元数据，rollout 管正文

Codex 的持久化是混合方案：~/.codex 下按功能拆成 6 个独立 SQLite 文件（线程元数据、日志、分页历史投影、记忆、目标、队列），schema 迁移用 sqlx Migrator 编译期嵌入 50 个迁移脚本；而对话正文则存在 rollout 文件里——一个 JSONL，按序记录完整事件流，恢复时把事件回放成状态。

这个设计的好处是职责分明：SQLite 提供可查询的结构化元数据（最近对话列表、token 用量），JSONL 提供无损的完整历史（包含所有中间事件、思考链、工具调用细节）。恢复一个会话等于"读 rollout 回放到某个检查点”，而不是依赖某个脆弱的序列化快照。

生态三件套：插件、Skills、Hooks

Codex 的扩展体系有三层，各司其职：

  • Hooks（codex-rs/hooks/）：进程外事件钩子，覆盖 PreToolUse、PermissionRequest、PostToolUse、SessionStart、SubagentStart 等 11 个生命周期节点，handler 可以是 shell 命令或 MCP 工具，按事件 + 正则 matcher 分发，支持同步/异步两种执行模式；返回 FailedAbort 可以直接阻断本次操作。这是"在事件点监听并干预"的机制；
  • Skills（codex-rs/skills/）：领域知识包，本质是一个 SKILL.md（YAML frontmatter + markdown 正文），通过 @skill-name 显式 mention 或被 implicit invocation 自动命中后，正文注入模型上下文；系统内置 skill 以 include_dir! 编译进二进制。这是"教模型做事"的机制；
  • 插件（codex-rs/core-plugins/）：值得注意的是它没有运行时代码 trait——插件是纯声明式包（PluginId 形如 computer-use@openai-bundled），manifest 声明它携带的 skills / MCP server / hooks / apps 四类资源，由 core 在启动时物化。marketplace 分发、command_migration 升级迁移、git_policy 等企业管控都发生在插件包层面。这是"打包并分发能力"的机制。

三者之外还有 MCP 客户端（codex-rs/codex-mcp/）：支持 stdio 与 streamable-http 两种传输、OAuth 认证，工具名统一加 mcp__<server>__ 前缀注册进模型可见工具目录。Codex 是 MCP 协议的头部消费方，它的实现（McpBinding 冻结工具目录版本、PreparedMcpCall 校验版本后才允许调用）对想自建 MCP 客户端的团队很有参考价值。

实现亮点：值得抄走的工程决策

抛开业务，Codex 的代码里有几个可迁移的设计模式：

  1. Trait object + feature flag 双驱动：features crate 集中管理 100+ 个带生命周期（Stage）的灰度开关，ModelProvider、AnySessionTask、ToolRouter 均为 trait object。新能力默认藏在 flag 后面，成熟一个打开一个；
  2. Op/Event 解耦多渲染器：TUI、JSONL、IDE 插件共享同一事件流，新增一个前端只意味着新增一个事件消费者；
  3. oneshot 挂起而非状态枚举：把"等待"建模成异步通道，天然支持并发挂起点，避免状态爆炸；
  4. RAII 资源占位：SpawnReservation 用 Drop 保证回滚，把资源上限的硬约束交给编译器；
  5. 配置分层：ConfigLayerStack 按优先级叠加多层配置，子 Agent 的覆盖受父级约束——权限收敛是结构性保证，不是约定；
  6. SQLite + JSONL 混合持久化：元数据可查、正文无损，恢复成本恒定。

这些决策没有一个是"新技术”，但组合在一起构成了一个可维护的 Agent 内核。这大概是整份源码最值得咀嚼的部分。

总结与展望

读完 Codex 源码，我最深的感受是：编码代理的壁垒不在模型，而在工程。事件循环的组织、安全边界的构筑、状态的可恢复性、多 Agent 的可控性——这些才是"能交给用户的生产力工具"和"demo"之间的分水岭。

也可以看到一些正在发生的变化：云端下发配置（cloud-config，HMAC 签名缓存 + 15 分钟后台刷新）让模型列表和 feature flag 可以绕过发版即时调整；app-server 协议在向 v2 迁移、实验性 API 用 #[experimental] 标注渐进发布；codex exec 的 --output-schema 预示着 Agent 正在变成可组合的编程原语。下一步如果把 Agent 类比成"新的进程”，那么 Codex 已经给出了进程管理器、权限系统、日志与恢复机制的完整参考答案。

对想深入的朋友，建议从三个文件读起：codex-rs/protocol/src/protocol.rs（事件协议，看懂一切的前提）、core/src/session/turn.rs（主循环）、core/src/exec_policy.rs（安全模型入口）。然后带着问题去读 TUI 的 select! 循环和 execpolicy 的规则解析，你会收获一套完整的 Agent 系统设计课。
